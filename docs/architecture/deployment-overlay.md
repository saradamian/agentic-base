# The deployment overlay

This repository is the software. Where it runs is somebody else's fact: a pipeline component,
environment manifests with hostnames, a registry and its pull secret, a catalogue entry. Those
belong to the platform that runs it, and they change on the platform's schedule, not ours.

The pattern here keeps them apart without keeping them out of sync.

## The shape

A **deployment repository** is this repository with a private **overlay** laid on top, and its
`main` contains our `main` as an ancestor. It stays current by merging upstream. Nothing is
copied, templated or regenerated; it is one git history with extra commits on it.

That merge is conflict-free for as long as one rule holds: **the overlay only adds files.** It
never modifies a file that exists upstream. `overlay.cfg` declares the paths an overlay owns, and
a guard on each side keeps the rule true:

- upstream, `tests/test_overlay_contract.py` refuses a change here that creates an
  overlay-owned path, so a contributor cannot land a pipeline file that a deployment would then
  collide with;
- downstream, `scripts/overlay.py check` refuses a missing overlay path, an upstream-owned file
  edited on the deployment side, and a site identifier anywhere outside the overlay. Code
  changes go upstream, through a pull request, and arrive by the next sync.

The tool is standard library only so it runs in any pipeline image.

## Why not the alternatives

A **mirror regenerated by squashing** cannot take pull requests, has no usable blame, and turns
every community file into decoration. This repository was one for a day.

A **submodule** puts the software under a subdirectory, and the platform's pipeline expects it at
the root. A **subtree** at the root is exactly this pattern with more machinery.

**Templating** the deployment repository from this one (copier, cookiecutter) re-derives what
git already tracks, and its update story is a weaker version of a merge.

**Substituting values at deploy time** (Flux post-build substitution, CI variables) is the right
refinement *inside* the overlay where the platform supports it: a hostname as a variable instead
of a literal. It does not remove the need for the overlay, because a pipeline `include` path
cannot be a variable and manifests have to exist somewhere.

## Composing a deployment repository

    python scripts/overlay.py compose --overlay <overlay checkout> --out <dir> \
        --upstream https://github.com/saradamian/agentic-base --ref main
    cd <dir> && git remote add deploy <platform project> && git push deploy main

`compose` clones upstream at the ref, records that commit as `refs/overlay/upstream`, copies the
overlay's tracked files on top, commits once, and runs `check`.

## Keeping it current

In the deployment repository, on a schedule or on demand:

    python scripts/overlay.py sync --ref main

`sync` fetches upstream, merges with a merge commit, advances `refs/overlay/upstream`, and runs
`check`. A conflict is reported by file with the reason, and the merge is aborted so the tree is
never left half-merged. The only conflict the contract allows is upstream growing a file at an
overlay-owned path, which is a contract violation to fix upstream, not a merge to resolve.

A deployment repository whose `main` is protected runs `sync` on a branch and opens a merge
request, so the platform's own gate runs on the merged result before it lands.

## What the overlay may contain

Anything at the declared paths. Typically: the pipeline definition and its templates, per-
environment manifests, the owners file in the platform's form, the catalogue entry, the
platform's dependency-update configuration, a runbook with the platform's prerequisites, and
`.overlay/forbidden.txt`, the site identifiers that must never reach an upstream-owned file.
The forbidden patterns live in the overlay and not here, because a list of what a site hides is
itself a description of the site.

## What it does not solve

Values that the platform's pipeline needs as *inputs* rather than files, such as build arguments
for the Dockerfile's registries, are the platform component's business; check what its inputs
allow before assuming a build argument reaches the build. And a change to a file both sides
legitimately need to own, such as a chart's default values, is a design question to settle by
making the value a parameter, not a merge to win.
